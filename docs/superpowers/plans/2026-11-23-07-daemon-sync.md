# Daemon Sync Implementation Plan (plan 07)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The daemon uploads each published project's chain to the Tally server (contract C7), commits its head hash every `COMMIT_INTERVAL_MS` while running, maps local projects to server ids, refuses to upload a chain that no longer matches a fresh derivation, and offers `tally login`, `tally sync`, `tally project link` and `tally repair`.

**Architecture:** One new module `sync.rs` (uploader + commit), one `api.rs` (the four HTTP calls, nothing else), one `credentials.rs` (per-project device tokens in one file). No new queue: what is unsent is exactly "entries of `published_ledger` for project P after the server's head", recomputed from `GET /head` each time. Blocking HTTP (`ureq`) called from the plan 03 run loop between polls; no async runtime. Tests use an in-process fake server built on `std::net::TcpListener` (no `hyper`, no `tokio`).

**Tech Stack:** Rust stable, existing crate deps, plus `ureq = { version = "2", default-features = false, features = ["tls"] }` (rustls). Dev: `tempfile` (exists).

**Spec:** `docs/superpowers/plans/README.md` (C4, C5, C6, C7, carried-forward items), `docs/superpowers/specs/2026-11-22-daemon-roadmap-design.md` (section 6), `docs/spec/scoring.md` §3, §6, `PITCH.md` ("Trust anchors", "Privacy"). Read all before every task.

## Global Constraints

- **Only two things leave the machine in `sync`:** `LedgerEntry` values (the spec §6 shape) and head hashes with a commit timestamp. No paths, local project ids, hostnames, usernames, event data or config values in any URL, header or body. The `User-Agent` is `tally/<CARGO_PKG_VERSION>` and nothing else. Task 8 enforces this with a test.
- **No second queue.** Never persist "pending uploads". The server's head, fetched fresh, decides what to send.
- **Never rewrite uploaded history.** No code path changes or deletes `ledger` or `published_ledger` rows (both are append-only already). Repair quarantines; it does not edit.
- **Entries never contain the server id.** The chain's `project` field stays the public name (C4/C6); the server id lives only in `projects.server_id` and in the URL path.
- **Bounded work:** batches of at most `BATCH_MAX = 500` entries; at most `MAX_409_RETRIES = 3` head refetches per project per sync; backoff capped at `BACKOFF_MAX_MS = 3_600_000`. Memory per sync is one project's published chain (tens of bytes per entry; well inside the 50 MB target).
- **Fail closed per project, not globally:** a `422`, a foreign server head or a divergence stops that project and is printed by `tally sync` and the run loop; other projects continue. A `401`/`403` stops only that project too (tokens are per project).
- All times are `i64` ms. The token is never printed, logged, or included in an error message.
- `cargo clippy -p tally-daemon --all-targets -- -D warnings` stays clean (CI already runs it).

## Review Focus

1. **Server unreachable for days, then reachable.** Expected: each failed attempt doubles the wait (`30 s`, `60 s`, ... capped at `BACKOFF_MAX_MS` = 1 h); commits that could not be sent are not queued (only the newest head matters, the next commit carries it); on reconnect one `sync` uploads every missing entry in batches of `BATCH_MAX` and the server head equals the local head. Memory does not grow while offline: nothing is buffered beyond the published chain already on disk. Tests in Tasks 6 and 7.
2. **Server head ahead of the local chain (another machine, or a restored backup).** Expected: if the server's `head_hash` is a hash in the local chain, upload resumes after it. If it is not in the local chain at all, the project stops with `SyncError::ForeignHead { project, server_head, server_count }`, nothing is uploaded, and `tally sync` prints that another device is writing this project's chain. The daemon never tries to "merge". Test in Task 6.
3. **A batch split across a crash** (server stored batch k, client died before reading `200`). Expected: on the next sync `GET /head` returns the last hash of batch k, which is in the local chain, so upload resumes at batch k+1; nothing is sent twice that the server already has, and if it is (a race), the server answers `409` and the client refetches the head. No local "sent" marker exists to get out of step. Test in Task 6.
4. **Token revoked.** Expected: `401` (revoked) or `403` (token of another project) stops that project with `ApiError::Unauthorized`, other projects continue, no retry storm (the ticker waits `BACKOFF_MAX_MS` before trying any project again), the token is left in place (a later `tally login` replaces it), and `tally sync` and the run loop print `sync: <project>: device token rejected; run tally login --server-id <id>`. The token never appears in output. Test in Task 6.
5. **Clock skew on the commit timestamp.** Expected: `ts` is the daemon's wall clock and is informational only; the trust anchor is the server's own receipt time (plan 06). The daemon does not adjust or refuse on skew; it sends `ts` as is, and a commit is accepted even when `ts` is far from server time. The test asserts the body carries the local `now_ms` unchanged. Task 7. Plan 06 stores `received_at` per commit, which is the anchor.
6. **A chain that no longer matches a fresh derivation.** Expected: before any upload, `finalize::check_derivation` (full entries, not 4 fields) and plan 05's `published::check` both pass, or the project is not uploaded and `tally repair` is suggested. Tasks 2 and 9.
7. **Older-ruleset chain after a server upgrade.** Expected: a chain the server already holds under an older ruleset keeps being appended to (the server verifies the chain, no re-scoring); a chain it never saw is refused with `422 unknown_ruleset`, stays local and is reported. Test: `an_older_ruleset_chain_is_appended_but_an_unknown_one_is_refused` in Task 6 (fake server: `set_current_ruleset`).
8. **Privacy.** Expected: every request body the fake server records is either empty (GET), `{prev_hash, entries}` with entries of exactly the spec §6 keys, or `{hash, ts}`. No local path, local project id, or config value appears in any URL or body. Task 8.

## Decisions I made (maintainer to confirm)

1. **Tokens in a file, not the OS credential store.** `<home>/device_tokens` (one line per server project, since plan 06 scopes a token to one project), created with mode `0600` on Unix (`std::os::unix::fs::OpenOptionsExt`); on Windows the file inherits the user-only ACL of `%LOCALAPPDATA%`. Reasons: the `keyring` crate needs D-Bus/Secret Service on Linux, which a headless or service-run daemon often lacks (plan 12 registers it as a service); it adds binary size; and a device token is narrow (append ledger entries to one project, revocable on the server). The SQLite store beside it is equally readable by the same user. Upgrade path: swap `credentials.rs` for `keyring` if the threat model adds same-user malware, which no file-based scheme defends against anyway.
2. **HTTP client: `ureq` 2, blocking, rustls, no `json` feature.** The run loop (plan 03) is a synchronous poll loop, so an async runtime (`reqwest` + `tokio`) would add a second concurrency model, several MB of binary and threads for four requests every few minutes. `ureq` adds roughly 1 to 2 MB (mostly rustls) and no background threads. Bodies are built with the existing `serde_json`. Timeouts: connect 10 s, total 30 s per request, so a hung server can stall one loop iteration by at most 30 s per request.
3. **Server id is given by the user, not discovered.** `tally project link <path> --server-id <id>` stores it in `projects.server_id`. Today the id comes from plan 06's `token:create` output (printed with the token); later from the web UI (plan 09). No endpoint for "find my project by name" exists in C7, and guessing by public name would let a typo upload to someone else's project. Several local ids with the same public name (worktrees, C4) are linked to the same server id; `sync` groups by public name and refuses if two local ids with one public name have different server ids (`SyncError::ConflictingLink`).
4. **Server chains are per `(project, ruleset)`,** matching plan 05's `published_ledger` table (read through `published_rows`). The daemon sends `?ruleset=<r>` on `GET /head` (plan 06 supports it) and uploads each ruleset chain separately, oldest first. Plan 06 accepts new chains only for its current ruleset but still accepts appends to an existing older-ruleset chain (append-only, chain-verified, no re-scoring), so an older chain not fully uploaded before a server upgrade can still be finished; a chain the server has never seen under an old ruleset is refused (`422 unknown_ruleset`), stays local and is reported. Commits carry only the head of the chain whose ruleset is `RULESET_VERSION` (plan 06 commits have no ruleset).
5. **`tally login --server-id <id>` reads that project's token from stdin** (paste the `token:` line from plan 06's `token:create`), checks it with one `GET /v1/ledger/<id>/head` when a server URL is configured, and stores it. No browser OAuth flow here: plan 09 owns Hack Club Auth and device-token issuing; it can later make `tally login` open a browser without changing anything else in this plan.
6. **Repair is quarantine plus a new epoch, and this plan ships only the local half.** See Task 9. The server half needs a C7 change that plan 06 does not have yet.

### Task 2: Full-entry divergence check (carried-forward item)

**Files:**
- Modify: `crates/tally-daemon/src/finalize.rs`

(Plan 04 changed `prepare` to drop skipped claims before comparing; keep that behavior in the shared function.) `prepare` compares only `(action_id, ts, verified_s, unverified_s)`, so a change in `kind`, `reasons` or `features` (a different build scoring the same events differently) goes unnoticed and would be uploaded. `project` stays excluded (naming a project later is allowed and tested); `prev_hash`/`hash` are not claim fields; `ruleset` is plan 05's `RulesetChanged` guard.

**Interfaces:**
- Comparison over `(action_id, ts, kind, verified_s, unverified_s, reasons, features)`.
- `fn first_divergence(ledger: &[LedgerEntry], claims: &[Claim], skipped: &BTreeSet<String>) -> Option<(usize, &'static str)>`: first index and the first differing field name in that order, or `"missing"` when the ledger is longer than `claims`. Claims whose `action_id` is in `skipped` (plan 04's `Store::skipped()` ids) are removed from `claims` first: they were never ledgered, so without this every store with a skip would report divergence and sync would stop.
- `FinalizeError::Divergence` gains `field: &'static str`; message `ledger diverges from re-scored claims at index {index} (action {action_id}, field {field})`. Existing tests use `..` and still compile.
- `pub fn check_derivation(store: &Store) -> Result<(), FinalizeError>`: the read half of `prepare` (horizon, events, score, name mapping, `skipped()` ids, `first_divergence`); writes nothing. Factor the shared part so `prepare` and `check_derivation` call one function.

**Interfaces:**
- `pub const BATCH_MAX: usize = 500; pub const MAX_409_RETRIES: usize = 3;`
- `#[derive(thiserror::Error, Debug)] pub enum SyncError`:
  - `Api(#[from] ApiError)`
  - `ForeignHead { project: String, ruleset: String, server_head: String, server_count: u64 }` - message `the server's chain for {project} has a head this device never wrote; another device may be syncing it`
  - `ConflictingLink { project: String }` - two local ids with one public name link to different server ids
  - `TooManyConflicts { project: String }`
  - `Derivation(#[from] FinalizeError)` (from `check_derivation`), `Published(#[from] PublishError)` (from plan 05), `Store(#[from] StoreError)`
- `pub struct ChainReport { pub project: String, pub ruleset: String, pub uploaded: usize, pub server_count: u64 }`
- `pub fn sync_chain(api: &Api, server_id: &str, project: &str, ruleset: &str, local: &[LedgerEntry]) -> Result<ChainReport, SyncError>`. Algorithm:
  1. `head = api.head(server_id, ruleset)?`.
  2. `pos` = 0 if `head.head_hash == GENESIS_HASH`, else 1 + the index of the local entry whose `hash == head.head_hash`. Not found, or `pos as u64 != head.count`, is `ForeignHead` (nothing uploaded). This covers "server ahead": a head that is in the local chain is simply resumed from.
  3. While `pos < local.len()`: `batch = &local[pos..min(pos + BATCH_MAX, len)]`, `prev` = `GENESIS_HASH` if `pos == 0` else `local[pos-1].hash`. `api.upload(server_id, prev, batch)`:
     - `Ok(h)`: `h.head_hash` must equal `batch.last().hash` (else `ForeignHead`); `pos += batch.len()`.
     - `Err(Conflict { .. })`: count it; over `MAX_409_RETRIES` is `TooManyConflicts`; else go back to step 1 (refetch, recompute `pos`). The `409` body's `head_hash` is not trusted alone: refetching keeps one code path.
     - `Err(TooLarge)`: halve this chain's batch size (start `BATCH_MAX`, floor 1; a single entry that is too large is returned as the error) and retry the same position. 500 entries of typical size are about 200 KB, but an entry can carry up to 32 features and 32 reasons, so 500 can exceed 1 MiB.
     - Any other error: return it (the caller decides on backoff). Entries already accepted stay accepted; the next run resumes from the server's head.
  4. Return the report.
- `pub fn sync_all(store: &mut Store, server: &str, tokens: &BTreeMap<String, String>) -> Vec<Result<ChainReport, SyncError>>`: one `Api::new(server, token)` per linked project; a linked project with no token is `Err(SyncError::NotLoggedIn { project })` (new variant, message `no device token for {project}; run tally login --server-id <id>`).
  1. `finalize::check_derivation(store)` then `published::sync(store, true)` (plan 05; it verifies both ledgers and appends any pending published rows). Either failing returns a single `Err` and uploads nothing: a diverged main ledger taints every project.
  2. For each `(name, ids)` in `store.server_ids()?`: more than one id is `Err(ConflictingLink)` for that name; otherwise group `store.published_rows(&name)?` by `entry.ruleset` (append order kept) and call `sync_chain` per ruleset, oldest ruleset first.
  3. An `ApiError::Unauthorized` stops that project's remaining chains; other projects continue (tokens are per project).
- Linked projects with no published rows yet are skipped silently (nothing to send).

**Interfaces** (`sync.rs`):
- `pub const BACKOFF_BASE_MS: i64 = 30_000; pub const BACKOFF_MAX_MS: i64 = 3_600_000;`
- `pub struct Backoff { failures: u32, next_ms: i64 }` with `new()`, `ready(&self, now_ms) -> bool` (`now_ms >= next_ms`), `failed(&mut self, now_ms)` (`failures += 1`, `next_ms = now_ms + min(BACKOFF_BASE_MS << (failures - 1), BACKOFF_MAX_MS)`; shift saturates, no overflow at 64+ failures), `unauthorized(&mut self, now_ms)` (`next_ms = now_ms + BACKOFF_MAX_MS`), `ok(&mut self)` (reset). - `pub fn commit_heads(store: &Store, server: &str, tokens: &BTreeMap<String, String>, last: &mut BTreeMap<String, String>, now_ms: i64) -> Vec<Result<(), SyncError>>`: for every linked project with a token, take the head of its `RULESET_VERSION` chain in `published_rows`; if it differs from `last[server_id]`, `api.commit(server_id, head, now_ms)` and record it on success. ### Task 9: `tally repair` (diagnosis now; epoch design for a follow-up)

**Files:**
- Create: `crates/tally-daemon/src/repair.rs`
- Modify: `crates/tally-daemon/src/lib.rs`, `crates/tally-daemon/src/main.rs`, `crates/tally-daemon/src/sync.rs`, `crates/tally-daemon/tests/cli.rs`

#### Design: what a user can safely do after `Divergence`

`Divergence` means a fresh `score()` of the stored events no longer reproduces the stored, chained entries. Causes, most likely first: (a) a new build scores the same events differently under the same `RULESET_VERSION` (a bug: the version should have been bumped); (b) an event entered the store without the late-event check (a bug or a hand-edited database); (c) the database is damaged.

Rules:
1. **Never rewrite.** Entries already in the ledger, the published branch or the server stay byte-for-byte. A verifier holding an old copy must keep seeing a prefix of what we later show.
2. **Cause (a) is a scoring change under an unchanged version.** Bumping `RULESET_VERSION` is a developer release decision, not a user repair step, so `tally repair` does not advise it. It reports `scoring changed` when the first differing field is `kind`, `reasons` or `features` and the seconds are equal, and the user follows rule 3 once available. Repair requires plan 10 Task 1b merged; until then `tally repair` only diagnoses.
3. **Otherwise: quarantine and start a new epoch.** The current chain is closed at its last entry. A new chain (epoch `n + 1`) starts at `GENESIS_HASH` and only scores events with `ts > finalized_through` at the moment of repair, so the first action after repair opens a new run (`FIRST_ACTION_S` interval, spec §3): conservative, never over-credits. The closed epoch keeps its hours (they were verified when written) and the server shows the project as repaired, with the reason, to the reviewer (spec §3: every project is human-reviewed).
4. **The reason is a fixed code, never free text** (it leaves the machine): `scoring-changed`, `store-damaged`, `events-edited`, `unknown`.
5. **No automatic repair.** The daemon stops uploading the affected projects and says why; only the user runs `tally repair --new-epoch --reason <code>`.

Local changes the follow-up needs (not in this plan) rebase on plan 10 Task 1b's `ledger_chains` table, not a second design: plan 10 has `epoch integer not null default 0` with `UNIQUE (ruleset, epoch)`, so a same-ruleset repair epoch is already allowed by the table. A repair then opens a `ledger_chains` row `(start_seq, ruleset, epoch + 1)` at `GENESIS_HASH`, with the closing reason code stored alongside; `published_ledger` chains key by `(project, ruleset, epoch)` likewise; `finalize` scores only events after the current epoch's `after_ts` and compares only the current epoch; `verify_ledger` verifies each epoch from `GENESIS_HASH`.

**Proposed C7 change for plan 06** (a proposal; plan 06 is not edited here):
- Chains are addressed by `(project, ruleset, epoch)`; `epoch` is a query parameter defaulting to `0` on `GET /head`, `POST /entries` and `POST /commit`.
- `POST /v1/ledger/{project}/epochs` body `{ "ruleset": "...", "closed_epoch": n, "closed_head": "<hash>", "reason": "<code>" }`. The server accepts it only if `closed_head` is its stored head for epoch `n` (the device has uploaded everything it will ever upload to it; otherwise `409 {head_hash}`), then refuses further appends to epoch `n` (`409`) and opens epoch `n + 1` at `GENESIS_HASH`. Returns `200 {epoch: n + 1}`. Hours: sum of verified seconds over all epochs; the reviewer view lists every epoch with its reason.
- Rejected alternative: encoding the epoch in the `ruleset` string (`2026.11-0+e1`) needs no API change, but the server picks the WASM scorer by ruleset, so it would break server re-scoring.
