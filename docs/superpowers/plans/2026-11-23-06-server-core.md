# Server Core Implementation Plan (plan 06)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A TypeScript service in `server/` that accepts per-project ledger chains from daemons, verifies them with the `tally-scoring` WebAssembly build, stores them append-only in Postgres, records hash commits, and serves the shields.io badge JSON. API v1 exactly as contract C7 in `docs/superpowers/plans/README.md`.

**Architecture:** One Bun process. `Bun.serve` with its built-in `routes` table (no framework). Postgres through Bun's built-in `Bun.sql` client (tagged templates, `sql.begin` transactions). Plain numbered SQL migration files applied by a small runner. The WASM package is built by `wasm-pack --target nodejs`, imported once at startup, and wrapped in `src/wasm.ts`. Request bodies are validated with `zod` strict schemas. Auth is a bearer device token, scoped to one project, created by an admin CLI and stored as a SHA-256 hash.

**Tech Stack:** Bun (one exact version of the 1.3 line, pinned in `package.json` `engines` and in CI), TypeScript (strict), `zod` (only runtime dependency), `@biomejs/biome` and `typescript` (dev), Postgres 16, `wasm-pack` + Rust stable for the WASM build.

**Spec:** `docs/superpowers/plans/README.md` (C6, C7, C8, C9), `docs/spec/scoring.md` §6 (ledger entry), `docs/superpowers/specs/2026-11-22-daemon-roadmap-design.md` ("Badge and publishing"), `PITCH.md` ("Cost"). Read them before every task.

## Assumes from earlier plans (code on `main` wins over the index)

- `crates/tally-scoring/src/wasm.rs` exports, under `--features wasm`:
  - `verifyChainJson(entriesJson: string, prevHash: string): number`: `-1` if valid, else the first failing index. Throws on JSON that does not parse into `LedgerEntry[]`. **It does not return the reason.** `ledger::verify_chain` checks `prev_hash` before `hash` for each entry, so the server derives the reason itself: `entries[i].prev_hash !== (i === 0 ? prevHash : entries[i-1].hash)` means `"bad_prev_hash"`, otherwise `"bad_hash"`. No crate change needed.
  - `rulesetVersion(): string` (returns `"2026.11-0"`).
- `LedgerEntry` (`crates/tally-scoring/src/ledger.rs`) has exactly the fields `v, ruleset, action_id, ts, project, kind, verified_s, unverified_s, reasons, features, prev_hash, hash`; `GENESIS_HASH` is 64 `'0'`; `chain(claims, prev_hash)` builds entries; `score(&[Event])` builds claims. **serde ignores unknown fields** (no `deny_unknown_fields`) and `canonical_json` hashes only the known fields, so an extra field passes `verifyChainJson` without being covered by the hash. The server must reject unknown fields itself (Task 4).
- `wasm-smoke/smoke.test.ts` already proves the exports load under Bun from a `--target nodejs` build. `.github/workflows/scoring.yml` shows the CI install steps (`dtolnay/rust-toolchain@stable` with `targets: wasm32-unknown-unknown`, `cargo install wasm-pack --locked`, `oven-sh/setup-bun@v2`). `wasm-bindgen` is pinned `=0.2.130` in the crate; `cargo install wasm-pack --locked` fetches the matching bindgen CLI.
- C6: the daemon (plan 05) builds one chain per published project; entries' `project` is the public name; each chain verifies alone from `GENESIS_HASH`. Plan 07 is the uploader; this plan does not touch the daemon.

## Global Constraints

- Everything lives under `server/` except: `.github/workflows/server.yml`, `crates/tally-scoring/examples/server_fixture.rs`, and (only if absent) the spec §6 wording check in Task 2. No other file outside `server/` changes.
- No second chain or hash implementation in TypeScript. Chain validity comes only from `verifyChainJson`. TypeScript may compare strings (head hash, ruleset, project name), never compute an entry hash.
- The ledger is append-only in the database itself: triggers reject `UPDATE`, `DELETE` and `TRUNCATE` on `ledger_entries` and `commits`. No code path issues those statements.
- An entry's `project` field is the project's **public name** and is stored exactly as received. The server's own project id (`projects.id`) is a separate column and appears only in URLs and foreign keys. Never rewrite an entry.
- All times are integer milliseconds (`bigint` in SQL, `number` in TS; values stay below 2^53). Hours are only formatted at the badge.
- Every response body is JSON. Errors are `{ "error": "<code>", ...detail }` with the codes listed in Task 4. No stack traces in responses.
- Logs are one JSON object per line on stdout. Never log the `Authorization` header, a token, a token hash, `DATABASE_URL`, or a request body.
- Ruleset (ruling 10): the server's current ruleset is `rulesetVersion()` of its WASM build. A batch must be one ruleset (every entry's `ruleset` equals `entries[0].ruleset`). A NEW chain is created only for the current ruleset; a batch for any other ruleset is accepted only if a chain for `(project, that ruleset)` already exists, and is then an append-only, chain-verified append with no re-scoring. Otherwise `422 unknown_ruleset`. A chain is identified by `(project, ruleset)`; a new ruleset starts a new chain from `GENESIS_HASH` (C7). This keeps a daemon's unuploaded `2026.11-0` entries uploadable after a server ruleset bump.
- Migrations are `NNN_name.sql` with three digits, run in name order (ruling 4): this plan uses `001_*` upward (only `001_init.sql`); plan 09 continues with `100`-`103`, plan 10 with `104_submissions.sql`.
- Dependencies: runtime `zod` only. Anything else needs a line in "Decisions I made" first.

## Review Focus

1. **Two uploaders racing on one project.** Two requests with the same `prev_hash` (the stored head) and different entries arrive together. Expected: the chain row is locked with `SELECT ... FOR UPDATE` inside the transaction; exactly one gets `200`, the other gets `409 {head_hash}` with the winner's head; `count` equals the winner's batch size. Test in Task 6 (`Promise.all` of two requests).
2. **A replayed batch** (the daemon timed out and re-sends). Expected: `200 {head_hash, count}` with unchanged head and count, nothing inserted. A batch whose first part is stored and whose rest is new appends only the new part. A batch that claims stored positions but whose hashes differ from the stored rows is `409`. Test in Task 6.
3. **A batch that is valid alone but not against the stored head** (its `prev_hash` is an older entry's hash, or `GENESIS_HASH` on a non-empty chain, with entries not stored). Expected: `409 {head_hash}`, nothing written. Test in Task 6.
4. **An oversized batch.** Expected: more than `MAX_BATCH` (1000) entries is `413 {error:"batch_too_large", max:1000}`; a body over `MAX_BODY_BYTES` (1 MiB) is `413 {error:"body_too_large"}` before JSON parsing. Test in Task 4 (schema) and Task 6 (HTTP).
5. **A ledger entry with unknown fields.** Expected: `400 {error:"invalid_body", issues}` where an issue's path names the extra key; nothing written. Reason: an extra field is not covered by the hash, so storing it would publish unverified data under a verified hash. Test in Task 4 and Task 6.
6. **A project that changes ruleset mid-chain.** Expected: a batch that mixes rulesets is `422 {index, reason:"unknown_ruleset"}` at the first entry whose `ruleset` differs from `entries[0]`; a batch for a ruleset that is not current and has no stored chain for the project is `422 unknown_ruleset` at index 0; a batch for an older ruleset WITH a stored chain appends (ruling 10). After a server upgrade, the old chain stays stored and appendable, a new chain row starts at `GENESIS_HASH` for the current ruleset, `GET head` defaults to the current ruleset's chain, and the badge sums verified seconds across all chains. Test in Task 6 (refusal, older-ruleset append) and Task 8 (sum across chains).

Also check: an entry whose `project` is not the URL project's public name is `422 reason:"project_mismatch"`; a token for project A used on project B is `403`.

### Task 4: Request schemas, error format, limits

**Files:**
- Create: `server/src/schema.ts`, `server/src/errors.ts`, `server/test/schema.test.ts`
- Modify: `server/src/wasm.ts` (import `LedgerEntry` from `schema.ts`)

**Interfaces:**
- `schema.ts` (all objects `.strict()`, so unknown keys fail):
  - `const Hash = z.string().regex(/^[0-9a-f]{64}$/)`
  - `export const LedgerEntrySchema = z.object({ v: z.literal(1), ruleset: z.string().min(1).max(32), action_id: z.string().min(1).max(256), ts: z.number().int().nonnegative(), project: z.string().min(1).max(200).nullable(), kind: z.string().min(1).max(32), verified_s: u32, unverified_s: u32, reasons: z.array(z.string().max(64)).max(32), features: z.record(z.string().max(64), z.number().int()).refine(o => Object.keys(o).length <= 32), prev_hash: Hash, hash: Hash }).strict()` where `u32 = z.number().int().min(0).max(4_294_967_295)`. Integers only, matching spec §6 "integers only"; a float fails here, never reaches WASM.
  - `export type LedgerEntry = z.infer<typeof LedgerEntrySchema>`
  - `export const UploadBody = z.object({ prev_hash: Hash, entries: z.array(LedgerEntrySchema).min(1) }).strict()`. Batch size is checked separately (before element validation) so the error is `413`, not `400`.
  - `export const CommitBody = z.object({ hash: Hash, ts: z.number().int().nonnegative() }).strict()`
- `errors.ts`:
  - `export class HttpError extends Error { constructor(public status: number, public body: { error: string; [k: string]: unknown }) }`

`{project}` in every `/v1` route is the server project id (`projects.id`, URL-safe), not the public name (which contains `/`). The daemon learns the id from `token:create` output (plan 07 stores it in its project mapping via `server_ids()`). Auth on every `/v1/ledger/*` route is `requireToken(sql, req, projectId)` (Task 5; plan 09 widens it to also accept user-scoped tokens, plan 10 reuses it). A project's owner is `projects.owner_id` (nullable, Task 2).

**Interfaces:**
- `ledger.ts`:
  - `export type Head = { head_hash: string; count: number }`
  - `export function checkBatch(entries: LedgerEntry[], prevHash: string, publicName: string, ruleset: string /* the batch ruleset, entries[0].ruleset */): { index: number; reason: string } | null`. Pure, no DB. In order, first failure wins: any entry with `ruleset !== ruleset` gives `unknown_ruleset` at its index; any entry with `project !== publicName` (including `null`) gives `project_mismatch`; then `verifyChain(entries, prevHash)` gives `bad_prev_hash` / `bad_hash`.
  - `export async function appendEntries(sql, projectId: string, body: { prev_hash: string; entries: LedgerEntry[] }): Promise<Head>` does, inside one `sql.begin` transaction:
    1. Let `R = entries[0].ruleset`. If `R === deps.ruleset` (default `rulesetVersion()`): `insert into chains (project_id, ruleset, head_hash) values (…, R, GENESIS) on conflict do nothing`. If `R` is older, insert nothing. Then `select id, head_hash, count, verified_s from chains where project_id = … and ruleset = … for update`; for an older `R` with no row, throw `HttpError(422, {error:"broken_chain", index:0, reason:"unknown_ruleset"})`. The row lock serializes uploaders on one chain (Review Focus 1). Appends to an older chain use the same overlap/replay rules and add the entries' own `verified_s` (no re-scoring).
    2. Find where the batch starts: if `body.prev_hash === head_hash`, `start = count`. Otherwise `start = 0` if `prev_hash` is `GENESIS`, else `1 + seq` of the stored row whose `hash = prev_hash`; if there is no such row, throw `HttpError(409, {error:"stale_prev_hash", head_hash, count})`.
    3. Overlap (replay, Review Focus 2): load stored hashes for `seq` in `[start, min(count, start + n))` in one query; each must equal `entries[k].hash` for the same `k`, else 409 as above (a different batch against an older head, Review Focus 3). The remaining `entries[count - start ..]` are new; their first `prev_hash` is the stored head because the batch already verified as one chain.
    4. Insert the new entries in one multi-row insert (`seq = count + i`, indexed columns copied from the entry, `entry = JSON.stringify(entry)`), then `update chains set head_hash, count, verified_s = verified_s + sum(new verified_s)`. Nothing new means no insert or update.
    5. Return the chain's `{ head_hash, count }` after the update (`count` as a JS number).
- Route in `app.ts`: `POST /v1/ledger/:project/entries`. Order: rate limit (Task 9 adds it; leave a call site), `requireToken(sql, req, params.project)`, `readJson`, batch size check (`Array.isArray(body?.entries) && body.entries.length > MAX_BATCH` gives `413 {error:"batch_too_large", max: MAX_BATCH}`, before element validation), `parse(UploadBody, …)`, load `public_name` for the project, `checkBatch` (failure is `422 {error:"broken_chain", index, reason}`), `appendEntries`, `200 {head_hash, count}`. One top-level try/catch in the router turns `HttpError` into its response and anything else into `500 {error:"internal"}` plus an `error` log line with the message only.
- The 409 and 422 bodies contain C7's fields (`head_hash`; `index`, `reason`) plus `error`, and 409 also carries `count` so the client can resync without a second request.

## Decisions I made (maintainer to confirm)

1. **Bun built-ins, no framework, no DB driver package.** `Bun.serve` `routes` covers five routes with path params; `Bun.sql` covers Postgres with transactions. Runtime dependencies: `zod` only. Fallback if `Bun.sql` misbehaves: the `postgres` package (same tagged-template style).
2. **Spec §6 `project` is the public name.** Made by plan 05; Task 2 verifies it. The hash covers `project`, and C6 publishes public-name chains, so the server keeps its own id in `projects.id` and never rewrites entries.
3. **URL `{project}` is the server id**, not the public name (which contains `/`). The daemon gets it from `token:create`.
4. **Unknown entry fields are rejected (400)**, because they are outside the hash. The crate is not changed; the server's strict schema enforces it.
5. **New chains only for the current ruleset; older chains stay appendable** (ruling 10). A new chain at any other ruleset is `422 unknown_ruleset`; appends to an existing older chain are chain-verified and stored without re-scoring, so unuploaded entries survive a ruleset bump. The badge counts all chains; `GET head` defaults to the current ruleset.
6. **Replays and overlaps succeed idempotently** (`200`, only new entries appended); anything diverging from the stored chain is `409` with `head_hash` and `count`.
7. **Commits are not checked against the stored chain**; they are receipts of the daemon's local head.
8. **Badge floors to 0.1 h** and is public with a 5-minute cache.
9. **Tokens:** `tly_` + 32 random bytes, SHA-256 stored, one project per token, revocable from the CLI.
