# wakatime-cli source check against Tally's synthetic heartbeat notes

Source: github.com/wakatime/wakatime-cli, shallow clone at commit 7ab26b5, read only (never built or run). Tally side read: docs/adapters/heartbeat.md and crates/tally-daemon/tests/fixtures/heartbeat/NOTES.md in this checkout (both say SYNTHETIC / UNVERIFIED; no later doc present here).

## Summary
The CLI source confirms most of Tally's route, auth and response-shape assumptions. It contradicts three: bulk batches are at most 10 (not 25), `line_additions`/`line_deletions` are never sent, and the "2 minute" rule is a global send throttle, not a per-entity rule. It never uses Bearer. It adds fields Tally does not list. Source reading only: real plugin captures are still needed.

## Findings

1. Heartbeat JSON (`Heartbeat` struct, pkg/heartbeat/heartbeat.go). `entity` (string) and `type` (file/domain/url/app) and `time` (float64 epoch seconds) and `user_agent` (string) are always emitted. Everything else is omitempty: `category`, `project`, `branch`, `language` (pointers), `lines`, `lineno`, `cursorpos` (*int), `is_write` (*bool), `dependencies` ([]string), `ai_line_changes`, `human_line_changes` (*int), `project_root_count`. Extra AI fields: `ai_input_tokens`, `ai_output_tokens`, `ai_cached_input_tokens`, `ai_session`, `ai_subscription_plan`, `ai_prompt_length`. There is NO `line_additions`/`line_deletions` in the outbound struct (they appear only in testdata/extra_heartbeats.json; no Go field matches, so the CLI ignores them on stdin). user_agent is `wakatime/<ver> (<os>-<core>-<platform>) <go ver> <plugin>` (`UserAgent()`); empty plugin becomes `Unknown/0`. Machine name goes in header `X-Machine-Name`, not the body (pkg/api/option.go `WithHostname`; value from `hostname` / `settings.hostname`, else os.Hostname, else "Gitpod").
2. HTTP (pkg/api/heartbeat.go). The CLI only POSTs `<api_url>/users/current/heartbeats.bulk` (JSON array, `Content-Type: application/json`, `Accept: application/json`). It never uses the single endpoint. Auth is always `Authorization: Basic base64(key)` (key alone; `BasicAuth` in pkg/api/auth.go); no Bearer, no `?api_key=` in this code. Success is only 201 or 202; 401 gives ErrAuth, 400 gives ErrBadRequest, anything else is a generic error. Body must be `{"responses":[[<body>,<status>],...]}`; each pair is `[{"data":{"id":...}}, 201]`. For non-2xx inner status, element 0 is parsed for errors. A non-array or malformed body is an error.
3. Config. `api_url` is read from flag `--api-url`, then `api-url`/`apiurl`/`api_url`/`settings.api_url` (pkg/params `loadAPIURL`), default `https://api.wakatime.com/api/v1`. `normalizeURL` strips trailing `/`, `.bulk`, `/users/current/heartbeats`, `/heartbeats`, `/heartbeat`. Tally's `http://127.0.0.1:25930/api` therefore yields `.../api/users/current/heartbeats.bulk`; NOTES says `/api/v1/...`, so the exact path depends on the user's `api_url` (Tally's docs omit `/v1`). Config file: `$WAKATIME_HOME/.wakatime.cfg` if set, else `~/.wakatime.cfg`, falling back to `$XDG_CONFIG_HOME/wakatime/wakatime.cfg` only if legacy file is missing (pkg/ini `FilePath`). Section `[settings]`; key `api_key`; env `WAKATIME_API_KEY`. Also `[api_urls]` regex-path map (`url|key`) can fan heartbeats out to extra destinations, and `[internal]` stores backoff state. Request timeout default 120 s. Other keys: `heartbeat_rate_limit_seconds`, `hostname`, `proxy`, `exclude`/`include`, `hide_*`.
4. Offline queue (pkg/offline/offline.go). It is bbolt (NOT sqlite): `offline_heartbeats.bdb`, bucket `heartbeats`, in `$WAKATIME_HOME` or `~/.wakatime/`. Constants: `SendLimit=10` per request (extra go to the queue), `SyncMaxDefault=1000` popped per sync, `maxRequeueAttempts=3` for DB push, rate limit 120 s. On a transport/status error the whole batch is re-queued. After a 201/202, per-heartbeat inner status 400 is dropped; other non-2xx are re-queued and sending stops. Missing results are re-queued. Backoff (pkg/backoff): wait = 15 * 2^retries seconds, state in `[internal] backoff_at/backoff_retries`; reset once over 3600 s; during backoff heartbeats go straight to the queue (exit code 112). No Retry-After or 429-specific handling found; 429 is just a non-201/202 error.
5. Flags (cmd/root.go): `--entity`, `--entity-type`, `--category`, `--time` (float), `--write`, `--plugin`, `--project`, `--alternate-project/-language/-branch`, `--lineno`, `--cursorpos`, `--lines-in-file`, `--local-file`, `--ai-line-changes`, `--human-line-changes`, `--extra-heartbeats` (reads ONE line from stdin, a JSON array; accepts `type` or `entity_type`, is_write bool or string), `--api-url`, `--key`, `--disable-offline`, `--heartbeat-rate-limit-seconds`. Sanitising (pkg/heartbeat/sanitize.go): hide-file-names replaces entity with `HIDDEN<.ext>` and nulls lineno, cursorpos, lines; hide-project-names/folder, hide-branch-names (branch nil), hide-dependencies, and credential stripping in URLs. A listener may see `HIDDEN.rs` as entity, so path-based project matching would fail for those users. Include/exclude patterns drop heartbeats before sending.
6. Rate limit / time (pkg/ratelimit, cmd/heartbeat). The CLI throttle is global, not per entity: if `internal.heartbeats_last_sent_at` is under 120 s old, the new heartbeat goes to the offline queue instead of the API, regardless of write flag or entity. The queue is flushed with the next send, in a batch of up to 10. I found no CLI-side "same entity, non-write, 2 minutes" dedupe; that logic is server-side (UNVERIFIED here). Consequence: a listener sees bursts of up to 10 heartbeats about every 2 minutes, with original `time` values, not a live stream. Time must come from the `time` field, never arrival time.
7. Diff against Tally NOTES.
   - Confirmed: bulk path `heartbeats.bulk`; Basic auth with key only; `time` float seconds; response `{"responses":[[{"data":{...}},201],...]}` one pair per input in order; 201/202 both accepted; non-2xx queues offline; `ai_line_changes`/`human_line_changes` exist; user_agent/plugin carried.
   - Contradicted: "max 25" bulk (CLI sends 10); `line_additions`/`line_deletions` as sent fields (absent); `?api_key=` and Bearer (not used by CLI; fine as extra server leniency); "queue offline" implies per-heartbeat 400 is also queued (it is dropped); `/v1` in path (depends on api_url).
   - Open: single endpoint (CLI never calls it, possibly other plugins do); GET status-bar calls (CLI has `statusbar.go`, `today`; not read); Host header value; Content-Type (application/json confirmed); that "accepted-and-dropped must answer 201" holds (confirmed: 201 with inner 201 is success).

## Recommendation
Update NOTES.md and the bulk handler to: accept any array length (expect at most 10, but do not cap at 25 as a hard error), accept `time` as float, treat missing optional fields as normal, ignore `line_additions`/`line_deletions`, and tolerate `HIDDEN.<ext>` entities. Document that `api_url` should be `http://127.0.0.1:<port>/api/v1` (or whichever prefix is routed) and route `.../users/current/heartbeats.bulk`. Reply 201 or 202 with one `[ {"data":{"id":...}}, 201 ]` pair per input, in order, and 400 only for a body the CLI cannot succeed on, since a 400 on the whole request surfaces as an error with batch re-queue. Expect delayed bursts, so time from `time`, not arrival. Still do one real plugin capture to confirm GET calls and the Host header.
